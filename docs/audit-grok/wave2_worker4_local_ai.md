### 1. Port squatting: `ensure_servers` / `ensure_llama_serving` treat any HTTP answer on :8080 as a healthy managed llama
- **Finding / Hypothesis:** `ensure_servers_for_route` (`local_ai.rs`, launch-only branch) skips spawn when `is_reachable("http://127.0.0.1:8080/v1/models")` is true. `ensure_llama_serving` then returns `(ModelSwitch::Switched, Vec::new())` with **no PID, no exe-under-root check, and no alias/completion probe**. `is_reachable` uses `curl -s` without `-f`, so any TCP/HTTP response (404, 503, foreign app) counts as success. Contrast with `install` / `wait_for_expected_llama`, which require `launched_llama_owns_listener` + exact `/models` alias + a real completion.
- **Rationale:** A killed `llama-server` whose port is taken by another process, an old projector-less orphan, or even a random HTTP stub on 8080 is recorded as “switched/serving”. The watchdog/boot path will not reclaim the port (`stop_listener_on_port` is not used here). UI/config keep talking to a stranger; vision/model identity silently diverge. The file’s own comment admits projector-less orphans are “accepted”.
- **Verification Method:** Bind a tiny HTTP listener on `127.0.0.1:8080` that returns `{}` for `/v1/models`. Call `ensure_llama_serving(root, choice)` and `ensure_servers(...)`. Expect `Switched` / empty `Vec<Child>` and no `llama-server.exe` under `root`. Repeat with a leftover `llama-server` started outside `root` (or after killing Suflyor if JobObject assignment failed).

### 2. Stale-listener false positive on engine verify-before-swap (:8077)
- **Finding / Hypothesis:** `verify_engine_runs` ignores `stop_listener_on_port(ENGINE_VERIFY_PORT, root)` (`let _ = ...`), then uses `wait_ready("http://127.0.0.1:8077/v1/models")` with **no** `launched_llama_owns_listener` / expected-model check. `wait_ready` is the same “any curl success” probe as `is_reachable`.
- **Rationale:** If a foreign (or leftover) process already answers on 8077, the staged binary need not bind or load a model. Verify returns true → `update_llama_engine` stops live :8080, copies staged exe/DLLs over the install dir, and stamps `.llama-build`. That is a successful swap justified by someone else’s socket. Inverse: a managed listener that will not die leaves verify flaky, but the dangerous direction is the false pass.
- **Verification Method:** Serve HTTP 200 on `127.0.0.1:8077/v1/models`. Point `staged_exe` at a non-runnable or dummy file (or a binary that fails to bind). Call `verify_engine_runs`. If it returns true, the update path will swap. Confirm `wait_for_expected_model_at` is **not** used here.

### 3. Bind race: launch without owning the port, child still returned
- **Finding / Hypothesis:** `ensure_servers_for_route` does not call `free_llama_port` / `stop_listener_on_port` before `launch_hidden`. Two workers (watchdog + switch, or install vs boot) can both observe “not reachable”, both spawn. One bind fails; the failed `Child` is still `push`ed. Whisper on :8081 is the same pattern.
- **Rationale:** `lifecycle_lock` exists for destructive :8080 transitions, but `ensure_servers` itself is not the lock. A dead child plus a foreign/winner listener makes later `wait_for_expected_llama` fail or, if the caller skips the wait (`ensure_servers` public API), AppState holds a zombie handle while :8080 is not theirs.
- **Verification Method:** Hold :8080 in `TIME_WAIT` or a non-HTTP `LISTEN`. Concurrently invoke `ensure_servers` twice. Inspect returned PIDs vs `netstat -ano` listener PID and `try_wait()` on each `Child`.

### 4. `stop_listener_on_port` netstat parsing and “unknown exe” conservatism
- **Finding / Hypothesis:** Owner check is `netstat -ano -p tcp` + `cols[1].ends_with(":{port}")` + `exe_path_for_pid` via PowerShell `Get-Process.Path`. Empty path (elevated/other-user/protected process) is treated as a stranger (`free_of_strangers = false`). `netstat` failure returns `false` (cannot reclaim). IPv6 `[::1]:8080` happens to match `ends_with(":8080")`.
- **Rationale:** Correctly refuses to kill strangers (install bails with a clear error). Combined with findings 1–2, a privileged or path-less listener **permanently blocks** reclaim on install/switch (`PortBusy`) while **boot `ensure_llama_serving` still reports healthy** if that listener speaks HTTP. Asymmetric: install is safe, runtime is gullible.
- **Verification Method:** Listen on 8080 as another user / without a resolvable `.Path`. Run `install` / `switch_local_model` (expect conflict/`PortBusy`) vs `ensure_llama_serving` (expect `Switched` if HTTP answers).

### 5. Model SHA is not a launch invariant except for 26B
- **Finding / Hypothesis:** Install/download paths call `verify_sha256` (delete-on-mismatch). Launch selection: `selected_llama_gguf` hashes **only** `Primary26B` via `cached_pinned_file_matches`. `Fallback12B` / `Legacy4B` use `file_has_expected_size` / `legacy_gguf_complete` (two allowed sizes). `mmproj_for_model` attaches projector on **size + build stamp only**. `reuse_if_available` returns true if `file_len(dest) >= expected` **without hashing dest** (callers usually hash afterward; `download_managed_model` skips SHA entirely for `LEGACY_GEMMA_SIZE_PREV`). `quality_model_present` (UI) is size-only by design.
- **Rationale:** Same-size corrupt/truncated-then-padded 12B/4B GGUF or mmproj is launched. Comments state a mismatched projector **crashes llama-server on load**. 26B same-size tamper is caught on worker paths and deleted (`discard_rejected_pinned_file`); 12B is the default fallback and is not. `>= expected` on dest can also treat an **oversize** leftover as complete until a later SHA (if any).
- **Verification Method:** After a clean install, flip one byte in `gemma-4-12B-it-qat-UD-Q4_K_XL.gguf` (keep length). Call `ensure_servers` / `restart_llama_server`. Expect spawn. Repeat for `mmproj-12b-F16.gguf`. Contrast with 26B: `quality_model_verified` should refuse and unlink.

### 6. Server binaries have host pin, not integrity; `curl -L` can leave the pin
- **Finding / Hypothesis:** `download_and_extract` only checks `is_trusted_release_url` on the **initial** GitHub URL (github.com / `*.githubusercontent.com`). Zip size comes from GitHub API `GhAsset.size` (serde default 0). **No SHA-256 / Authenticode** of `llama-server.exe` / DLLs. `curl_resumable` uses `-L` with no `--proto` / redirect allowlist. `curl_resumable` stops when `file_len >= expected`, so a larger blob is accepted and extracted (`extract_zip` has zip-slip checks only).
- **Rationale:** Compromised GitHub release, tampered API JSON, or a 302 off the allowlisted host yields a malicious `llama-server.exe` bound to localhost with OpenAI-compatible APIs (prompt/exfil surface). Engine update’s runtime smoke test reduces “won’t start” risk, not “starts and is evil”. Models are saved by pinned SHA; **engines are not**.
- **Verification Method:** Unit-test `is_trusted_release_url` vs a GitHub URL that 302s to `https://evil.example/llama.zip`. Confirm `curl_resumable` is invoked with `-L` and no redirect allowlist. Confirm no `verify_sha256` on zips/exes. Optionally serve a zip whose uncompressed payload is a renamed notepad; `verify_engine_runs` may still pass if `/v1/models` is mocked (finding 2).

### 7. Unpinned `/main` artifacts are only safe if SHA runs
- **Finding / Hypothesis:** `MMPROJ_URL`, `WHISPER_URL`, `GIGAAM_MODEL_URL` resolve `/main/` (mutable), while Gemma 12B/26B GGUFs use immutable revision hashes. SHA pins exist and install verifies them. Launch does **not** re-hash whisper/mmproj (whisper: file exists; mmproj: size).
- **Rationale:** A `/main` move fails install SHA (good). A same-size replacement after install is loaded (crash or wrong weights). GigaAM vocab is bundled (`include_bytes!`) — that path is solid; the ONNX model is not re-checked at STT start in this file.
- **Verification Method:** Install, then same-size overwrite of `ggml-large-v3-turbo-q8_0.bin` / mmproj; restart via `ensure_servers`. Confirm no `verify_sha256` on that path.

### 8. Unknown / custom hardware: no `-ngl` / `-np` caps → VRAM and RAM blow-up
- **Finding / Hypothesis:** `llama_server_args` applies `-ngl`, `--no-mmap`, `-np 1` only when `profile != Unknown || macos`. On Windows `HardwareModelProfile::Unknown` (6 GB GPU, 10 GB RAM, AMD without matrix, `force_cpu` discovery miss, custom GGUF), **no** `-ngl 0`, **no** `-np 1`, **no** `-ncmoe`. `select_hardware_model_profile` never rounds “nearby” cards into the matrix except ±1 GiB on 8/12/16. `download_managed_model` explicitly does not block 26B. `ModelSwitch::HardwareUnsupported` is **never returned** by `switch_local_model` in this source. `LocalContextPreset::context_tokens` ignores `prep` (`_prep`) and only caps by **live** `profile.context_tokens(false)` — Unknown live cap is 8192, but Unknown also skips the ngl/np block.
- **Rationale:** llama.cpp defaults typically offload all layers (`-ngl` high) and may open multiple slots. 12B/26B + other GPU apps → driver TDR, shared-memory spill, pagefile thrash, hard freeze. `--no-mmap` on **known** profiles forces a full RAM commit (10.5 GiB file + KV); 96K context on `Primary26Vram16` is owner-approved but still unbounded vs competing VRAM (`warn_if_nvidia_vram_busy` is warn-only at ≥2 GiB used). Job object has **no** memory limit. Whisper launch has no thread/memory caps.
- **Verification Method:** On a machine that reports VRAM not in {8,12,16}±1 or with a custom GGUF, log `local-ai launch: profile=Unknown` and the argv: absence of `-ngl`/`-np`. Load 26B after `download_managed_model`. Monitor `nvidia-smi` / commit charge while sending concurrent `/v1/chat/completions`. Confirm `switch_local_model` does not return `HardwareUnsupported`.

### 9. Context / KV path can still OOM inside the “safe” matrix
- **Finding / Hypothesis:** Confirmed profiles set `-c` up to 32768 (12B / 26B-8GB live) or 98304 (16 GB live). Prep route adds `-ctk q8_0 -ctv q8_0` only for 8/12 GB 26B, but **does not increase `-c`** because `LocalContextPreset` drops `prep`. Parallel is 1 on known profiles. There is no pre-flight `free VRAM >= estimated_total_vram_mib`. `wait_for_nvidia_vram_release` is 10s then fail — it does not cap the next load.
- **Rationale:** A 96K F16 KV on 26B was estimated ~675 MiB / 32K in comments; plus `--no-mmap` weights, plus a busy desktop, still hits `CUDA OOM` / Windows DWM freeze. Failure is process crash, not a managed downgrade, unless the **install** readiness fallback (26B→12B→CPU) runs. Watchdog `ensure_llama_serving` will see a dead port and relaunch the **same** too-large choice (loop).
- **Verification Method:** Profile `Primary26Vram16`, preset `K96`, fill context with a long prompt while another app holds ~4 GiB VRAM. Watch for crash + `ensure_llama_serving` relaunch loop. Compare install’s GPU→12B→CPU fallback (present) vs runtime restart (no equivalent ladder except 26B→12B in `restart_llama_server_for_route_inner`).

### 10. Process spawn: `CREATE_NO_WINDOW` is delegated; JobObject is best-effort and skippable
- **Finding / Hypothesis:** Servers go through `launch_hidden` → `spawn_hidden` → `hidden_command` → `crate::download::no_window` (not in this scope). `assign_to_lifetime_job` runs only in `launch_hidden` (not `spawn_hidden` curl/tar). Job is `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` only; `CreateJobObjectW` / `SetInformationJobObject` / `AssignProcessToJobObject` failures are logged and ignored (`raw == 0` return). Nested-job failure is common if Suflyor itself is already in a job (debuggers, some installers, Task Scheduler).
- **Rationale:** If `no_window` is `CREATE_NO_WINDOW`, console flash is covered for servers. If Job assign fails, force-kill/upgrade of the overlay **orphans** `llama-server` on :8080 — exactly the situation `ensure_servers` then misreads as healthy (finding 1). Curl downloads are not job-tied (orphan curl, not port squat). `terminate_child_tree` uses `taskkill /T /F` only when a handle still exists.
- **Verification Method:** Inspect `download::no_window` for `CREATE_NO_WINDOW` (and that it is not overwritten). Launch under an outer Job Object; confirm log `AssignProcessToJobObject failed` and that killing Suflyor leaves `llama-server` LISTENING. Confirm `spawn_hidden` children are not assigned. Query Job membership with `Get-CimInstance Win32_Process` / Sysinternals.

### 11. Whisper readiness is weaker than llama (zombie / foreign :8081)
- **Finding / Hypothesis:** Install waits with `wait_ready(WHISPER_BASE_URL/models)` — no child-alive, no PID-owns-port, no model id. `ensure_servers` only checks `is_reachable` on :8081.
- **Rationale:** Same squat class as llama, lower impact (STT), but a foreign 8081 makes the app skip `whisper-server` forever. Install can report success against a pre-existing listener after `stop_listener_on_port` failed… actually install bails if stop fails. Boot will not.
- **Verification Method:** HTTP stub on 8081; call `ensure_servers(..., want_whisper=true)`. Expect no `whisper-server.exe` spawn.

---

**Highest-severity cluster:** runtime orchestration trusts **socket liveness**, not **ownership + pinned artifact + child identity**. Integrity is strong at **download** for GGUF SHA pins and zip-slip, weak at **launch** (12B/mmproj/whisper size-only) and for **unsigned engine zips**. Resource limits exist only on the owner’s NVIDIA matrix; Unknown/custom/26B-on-small-GPU can take down the machine, and JobObject does not constrain memory.
