### 1. Archive Traversal (Zip/Tar Slip)
- **Finding / Hypothesis:** `extract_tar_bz2` in `overlay-backend/src/download.rs` (`extract_tar_bz2`, `Command::new(system_bsdtar()).arg("-xf").arg(tarball).arg("-C").arg(dest_dir)`) invokes Windows `System32\tar.exe` / POSIX `tar` with **no member allow-list, no `..` / absolute-path rejection, no symlink/hardlink disable, and no post-extract containment walk**. Callers (`ocr_install.rs` `install`: `extract_tar_bz2(&tarball, &root)` into `%APPDATA%\suflyor`) trust the archive root to be `tesseract/`. A crafted `.tar.bz2` can write outside `dest_dir` (parent of `tesseract/`, Startup, other profile dirs) or plant a symlink/junction then overwrite through it. Fallback `PathBuf::from("tar.exe")` in `system_bsdtar()` also allows PATH-hijacked extractors to ignore `-C` entirely.
- **Rationale:** Pinned SHA-256 is **not** a substitute for Zip/Tar-Slip defense (the stated invariant). If the pin is updated against a compromised GitHub asset, or the tarball is swapped post-verify (Finding 2), `bsdtar`/`libarchive` will happily materialize `../` members relative to `-C`. `ocr_install` only deletes `root/tesseract` on failure; files slipped **outside** `dest` are left behind. If the archive also contains `tesseract.exe` + `tessdata/rus.traineddata`, `dest_has_engine` returns true and the UI reports success while the traversal payload remains. There is no zip path in this scope; the only unpacker is this tar helper (shared by OCR and any other installer that composes it).
- **Verification Method:** Build a `.tar.bz2` whose first member is `../../../../Temp/suflyor-slip-pwn.txt` (and optionally a valid `tesseract/tesseract.exe` + `tesseract/tessdata/rus.traineddata`). Point `extract_tar_bz2` at a temp `dest_dir` (or temporarily replace `BUNDLE_SHA256` / skip verify in a unit test harness). Confirm the file appears **outside** `dest_dir`. Repeat with a symlink member `tesseract` → an absolute path, then a regular file `tesseract/evil`. On a PATH without `System32\tar.exe`, drop a stub `tar.exe` that creates files ignoring `-C` and confirm it is spawned.

### 2. Checksum Verification TOCTOU
- **Finding / Hypothesis:** Integrity is bound to a **path**, not a stable fd. `verify_sha256` (`download.rs`) does `std::fs::read(path)` then returns; `ocr_install.rs` later calls `extract_tar_bz2(&tarball, &root)` on the same path. `teratts_install.rs` `install_with` does `verify_file(entry, &partial)` then `std::fs::rename(&partial, &staged)` (and resume via `verify_file` on `staged` by path). `update.rs` `download_installer` hashes **in-memory bytes** (good) then `std::fs::write(&path, &bytes)` and later `run_installer` does `Command::new(path).spawn()` with **no re-hash, no exclusive lock, no Authenticode**. Predictable locations: `%APPDATA%\suflyor\tesseract-ocr.download.tar.bz2` and `%TEMP%\suflyor-update\suflyor-slint-setup.exe`.
- **Rationale:** Classic time-of-check/time-of-use. Same-user code (browser, another installer, a junction planted in `Temp`/`APPDATA`) can replace the file after a matching hash and before extract/exec. Hash-then-write in the updater closes the download/verify race, but **write-then-exec** reopens it: the process that will overwrite the running binary is launched by path. `verify_sha256` also slurp-hashes (no `FILE_SHARE_NONE` / `O_EXCL`), so a writer can change bytes after `read` returns. Teratts is stronger (stage + `.part` + marker-last publish) but still verifies a path, then renames that path; a replace of `*.part` between `verify_file` and `rename` publishes attacker bytes. Runtime `check_dir` only compares **sizes**, so post-install mutation of ONNX graphs is invisible.
- **Verification Method:** Hook a test that: (1) writes a valid tarball, (2) calls `verify_sha256`, (3) overwrites the path with a slip tarball, (4) calls `extract_tar_bz2` — extraction must follow the **second** file. For the updater: after `download_installer` returns, overwrite `%TEMP%\suflyor-update\suflyor-slint-setup.exe` before `run_installer` and show the swapped PE is spawned. Fix shape to assert: `File::open` → hash `Read` on that handle → extract/exec the same handle (or `rename` a just-hashed file from a 0700 dir with `O_EXCL`).

### 3. Insecure Network Protocols (`curl -L` / reqwest redirects)
- **Finding / Hypothesis:** `curl_download` (`download.rs`) only gates `url.trim().starts_with("https://")`, then runs `curl.exe -L --fail ... --retry-all-errors -o <dest> <url>` with **no `--proto =https`, `--proto-redir =https`, `--max-redirs`, `--proto-redir -all,https`, host allow-list, or bind/proxy restrictions**. `update.rs` `is_trusted_download` is a solid static allow-list (HTTPS, port 443, no userinfo, exact `github.com/{REPO}/` or GitHub CDN hosts), but `reqwest::Client` **follows redirects by default** after that check; CDN hosts `objects.githubusercontent.com` / `release-assets.githubusercontent.com` accept **any path**. Teratts URLs are `https://huggingface.co/...` and routinely 302 to `cdn-lfs.huggingface.co` — still via unrestricted `curl -L`.
- **Rationale:** The HTTPS prefix applies only to the **first** hop. A 30x from GitHub/HuggingFace (open redirect, compromised edge, captive portal, TLS-intercepting “antivirus”) can send curl to `http://…`, `file://`, `dict://`, or loopback/link-local (`http://127.0.0.1/`, `http://169.254.169.254/`). That is SSRF / protocol downgrade / NTLM leak even when the **final** bytes fail SHA-256 (integrity may hold; the request still happens). `--retry-all-errors` amplifies the side effect. Updater hashing is fail-closed against **content** swap (`expected_sha256_for` + `Ok(None)` / `Err` bail), so a redirect to malware should not *install* unless GitHub’s API digest is also lying — but it does not stop the redirect fetch itself, and `is_trusted_download` never sees the Location host. `curl_download` is the common path for multi-GB models; a CDN 302 to HTTP is enough to violate “HTTPS only.”
- **Verification Method:** Local HTTP 302 server: initial URL `https://…` (or a test double) → `Location: http://127.0.0.1:<probe>/stolen`. Confirm `curl_download` hits the probe (packet capture / probe logs). Repeat with `Location: file:///C:/Windows/win.ini`. For reqwest: `is_trusted_download("https://github.com/PavelLizunov/suflyor/releases/download/v0.0.0/suflyor-slint-setup.exe") == true` then mock that URL to 302 `https://evil.example/x.exe` and show `Client::get` follows (disable redirects or pin `redirect::Policy::custom` that re-runs `is_trusted_download` on every hop). Positive control: curl `--proto-redir =https --max-redirs 3` must refuse the HTTP hop.

### 4. Partial / Staged Downloads and Invalid Install State
- **Finding / Hypothesis:** `curl_download` deletes `dest` only if curl’s **exit status** is non-success; there is no `--remove-on-error`, no fsync, no size predeclaration. Kill/crash during transfer leaves a truncated object. `ocr_install.rs` does `remove_file(&tarball)` at start (good) but **does not wipe `dest` before extract**, early-returns if `is_installed()` (resolver may treat a half-unpacked tree as ready), and on extract failure only `remove_dir_all(&dest)` — not other members dumped into `root`. Teratts is much better (`.part` → verify → rename, wipe staging on error/cancel, marker last, quarantine broken releases) but: leftover `{path}.part` after hard kill is overwritten not resumed (`curl` has no `-C -`); `check_dir` is size-only; `install` early-returns on marker + sizes without re-hashing. Updater: hash-fail bails **before** write, so a **previous** `suflyor-slint-setup.exe` in `%TEMP%\suflyor-update\` remains executable; a torn `std::fs::write` can leave a truncated MZ that still passes a naive “file exists” UI if a caller does not go through `download_installer` again.
- **Rationale:** Truncated curl output that still exits 0 (reset after last byte claimed, disk full then “success” on retry, proxy 200 HTML) is caught by SHA-256 **if verify runs**. If the process dies between verify and extract, next OCR run may skip work via `is_installed()` once `tesseract.exe` + `rus.traineddata` exist, even if the rest of the runtime is missing or mixed with an older extract. Failed layout check deletes `tesseract/` but not slip/junk files in `data_root`. Teratts staging + quarantine is the right pattern; OCR/updater do not share it. Predictable TEMP installer + no cleanup on digest failure is a stale-binary hazard for `run_installer`.
- **Verification Method:** (OCR) Start `install`, kill during `curl.exe`; confirm leftover `tesseract-ocr.download.tar.bz2`; restart — must re-download (should, due to initial `remove_file`). Kill during extract after the two `dest_has_engine` files exist; restart and show `AlreadyInstalled` despite missing other runtime files. Extract an archive with extra files at tar root; fail `dest_has_engine`; list `data_root` for leftovers. (Teratts) Kill after `.part` write; confirm next run re-downloads that file and does not publish without marker; hash-mismatch test already in-module (`install_with_wipes_staging_on_hash_mismatch`) — keep it. (Updater) Place a dummy `suflyor-slint-setup.exe` in the temp dir, force `expected_sha256_for` failure, confirm the dummy is still there and spawnable.

**Net:** Teratts publish/quarantine and updater fail-closed GitHub digest are real mitigations; they do **not** cover tar-slip, curl/reqwest redirect policy, or path-TOCTOU before extract/exec. The invariant “verify pinned hash **before** extract/exec **and** refuse Zip/Tar-Slip” is only half-implemented: hashes exist; containment and same-fd binding do not.
