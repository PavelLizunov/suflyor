### 1. Stateless `resample_and_quantise` drops remainder and resets phase every chunk
- **Finding / Hypothesis:** `resample_and_quantise` (`overlay-backend/src/audio.rs`, and the duplicate in `audio_macos.rs`) is a per-call boxcar decimator with **no fractional-index / remainder state**. After each ~200 ms emit, Windows does `f32_buf.clear()` and macOS does `accum.clear()`, so leftover native samples are discarded. The 3:1 fast path uses `full_chunks = input.len() / 3` and returns, dropping `len % 3` samples. The general path uses `out_len = (input.len() as f64 / ratio).floor()` and windows `[floor(i*ratio), floor((i+1)*ratio))`, then throws away the tail. **WSOLA is not used on capture at all** (`suflyor-wsola` is a playback timestretch crate; `StreamingWsola` never appears in the capture/WAV path).
- **Rationale:** Phase is not carried across chunk boundaries. At 48 kHz the 3:1 path is often exact; at **44.1 kHz → 16 kHz** (`ratio = 2.75625`) a WASAPI/CoreAudio period that does not land on a 200 ms multiple leaves 1–2 native samples unconsumed every chunk. That is a phase jump plus a short output vector. There is no anti-alias filter beyond a 2–3 sample average, so energy above 8 kHz folds into the speech band. Over a long meeting this is not just “a bit of aliasing”: STT chunks get boundary artifacts, and the recorder (below) will treat the short PCM as a timeline hole.
- **Verification Method:** Unit-test a 44.1 kHz 1 kHz sine in **non-multiples of 8820** (e.g. 8820+132, 8820+441) split into successive calls with `clear()` between them; assert leftover samples, output length vs `input.len()/ratio`, and a discontinuity in the reconstructed 16 kHz phase. Compare against one-shot resample of the concatenated buffer. Run a 1-hour 44.1 kHz capture and diff `sum(pcm_i16.len())` vs `timestamp_ms * 16`.

### 2. Non-integer ratios and wall-clock vs sample-count drift over hours
- **Finding / Hypothesis:** Chunk timestamps are `start_ts.elapsed().as_millis() as u64` (Windows `capture_thread`) / `session_start.elapsed().as_millis() as u64` (macOS workers) — **QPC/wall monotonic time, not IAudioClock / sample position**. `SessionRecorder::plan_pad` then treats `timestamp_ms` as the chunk **end** on a 16 kHz grid (`timestamp_ms * 16000 / 1000 - skew`). Device clock vs `Instant` (tens of ppm) plus dropped resampler remainder plus `as_millis()` truncation (±1 ms = ±16 samples) make `written` and wall-clock diverge. Fast device clocks never increase `skew` (pad is forward-only); slow clocks accumulate pad until `MAX_TOTAL_PAD_SAMPLES` (30 min), after which the WAV is permanently early.
- **Rationale:** A 50 ppm rate error is ~180 ms/hour. Combined with ~2 leftover samples / 200 ms at 44.1 kHz (~0.8 s of PCM missing per hour), `plan_pad` inserts 1–4 zeros **between every chunk** when PCM is short of the timestamp span — periodic micro-gaps in `mic.wav`/`system.wav`, broken `sample_offset == audio_ms`, and eventual «метки времени неточны» behavior even in a continuous meeting with no real silence. Mic and system Windows threads each have their own `start_ts`; a recovery sleep on one source only (1 s) desynchronizes the two WAV timelines.
- **Verification Method:** Capture 2+ hours at 44.1 kHz and 48 kHz; log per-chunk `(timestamp_ms, pcm_i16.len(), cumulative_samples)`. After session stop, compare WAV lengths to last `timestamp_ms`. Inject a synthetic 100 ppm rate error in a unit test around `plan_pad` + fake chunks every 200 ms with `len = 3197` vs `3200`.

### 3. Bluetooth / default-device death hangs in `wait_for_event` if notifications are missing
- **Finding / Hypothesis:** In `capture_thread`, `event.wait_for_event(250).is_err()` only logs a 60 s `audio_no_frame heartbeat ... action=wait` and **`continue`s**. It never reads the capture client, never treats idle as `CaptureExit::Recover`, and never times out into reopen. `AUDCLNT_E_DEVICE_INVALIDATED` is only observed on `read_from_device_to_deque`. If `RouteWatcher::register()` failed (`route_watch = None`) or Windows does not fire IMM notifications (some BT sleep/profile switches), a dead stream that simply stops signaling events **loops forever**.
- **Rationale:** This is the “hang silently in a wait loop” case. Loopback silence (Zoom paused, nothing rendering) is indistinguishable from a sleeping BT headset. Mic-side, 60 s+ of no frames is almost never “valid silence” in a meeting, yet the thread still waits. Recovery, when it does happen, always `thread::sleep(Duration::from_secs(1))` in `capture_with_recovery` — a guaranteed 1 s hole per reconnect.
- **Verification Method:** Start capture, then disable the endpoint in Device Manager or pull BT power **after** mocking `RouteWatcher::register` to fail. Confirm logs show heartbeats, no `audio_recovery begin`, and no further `AudioChunk`s. Repeat with notifications enabled (expect reopen + 1 s gap). PTT path: hold PTT and disconnect — `record_source_until_stop` swallows `read` errors (`continue`) and has **no** `RouteWatcher`.

### 4. Recovery policy misses communications-role default changes and DeviceAdded
- **Finding / Hypothesis:** `RecoveryPolicy::decide` (`audio_route.rs`) reopens on `DefaultDeviceChanged` only when `flow == self.flow && role == RouteRole::Console && !current(id)` and selection is `FollowDefault`. `eCommunications` / `eMultimedia` map to `RouteRole::Other` → **`Unrelated`**. `OnDeviceAdded` is a no-op. Pinned devices ignore default changes (`IgnorePinnedDefaultChange`) and, after unplug, `find_device_by_name` errors in a 1 Hz retry with **no fallback to default**.
- **Rationale:** Teams/Zoom often bind to the **communications** default. Switching a BT headset during a live meeting updates `eCommunications` first (or only). Follow-default capture keeps the old render/capture client until Console changes or the client errors. Pinned “Headset (BT)” stays dead until that exact friendly name returns; duplicate friendly names already warned in `enumerate` make reopen pick the wrong endpoint (silent wrong-device capture).
- **Verification Method:** Two playback devices; set Console vs Communications defaults independently while `FollowDefault` capture runs; assert which notifications produce `Recover`. Unplug a pinned device and confirm 1 s error loop without fallback. Plug two devices with the same friendly name and confirm `find_device_by_name` returns index 0.

### 5. macOS route recovery can detach a live tap and retry forever
- **Finding / Hypothesis:** `system_capture_worker` sets `SYSTEM_WORKER_PENDING` before `system_capture_stop` + `reopen_system`. `CaptureHandle::drop` **detaches** if `state == PENDING` (TCC-avoidance). `reopen_system` / `retry_route_start` retry every `ROUTE_RESTART_DELAY` (500 ms) with **no attempt cap** and no `RetryResult::Stop` on TCC/`SYS_START_DEVICE` (unlike mic permission).
- **Rationale:** Stopping a meeting during an AirPods route rebuild leaks a worker + partial aggregate/tap until process exit. Persistent TCC denial or missing Screen Recording permission becomes a forever 2 Hz native `system_capture_start` storm on `audio-sys`. First-run consent can also leave capture “started” from the UI’s point of view (`start_capture` does not wait on system start) with `SystemCaptureState::Pending` then `Failed`.
- **Verification Method:** Trigger `system_capture_take_route_change != 0` (unplug AirPods) and drop `CaptureHandle` immediately; assert whether the process still holds an aggregate device / IOProc. Deny Screen Recording and watch retry cadence + CPU. Confirm UI `system_capture_state()` during TCC.

### 6. PTT `record_source_until_stop` is an unbounded f32 accumulator
- **Finding / Hypothesis:** Windows PTT: `all_f32: Vec<f32>` reserved for 30 s then **grows without cap** until `stop`. macOS PTT: `accum.extend_from_slice` in a 20 ms drain loop with **no max length**. Live STT path is bounded (`f32_buf` ~200 ms, mpsc 128, `try_send` drop). Recorder queue is 256 and also drops. PTT is the exception.
- **Rationale:** Stuck PTT key, a lost `stop` flag, or a 2-hour “hold to talk” is `rate * seconds * 4` bytes (48 kHz stereo-as-mono ≈ 0.7 GB/hour) plus a second allocation in `resample_and_quantise`. A stalled consumer does **not** grow the live capture queue (good), but PTT does not share that discipline. `SessionRecorder` Drop `join()`s the writer: a stuck disk can park session teardown even though `feed` is non-blocking.
- **Verification Method:** Call `record_source_until_stop` and never set `stop` (or delay 10+ minutes); plot `all_f32`/`accum` capacity. Hold PTT in the UI for 30+ minutes. Pause disk (Windows: pause the recorder thread via debugger) and drop `SessionRecorder`; confirm Drop hang.

### 7. Negotiated mix format is never read back; byte stream is assumed f32 mono LE
- **Finding / Hypothesis:** Windows `capture_thread`, `record_source_until_stop`, and `record_mic_blocking` call `get_mixformat()` **before** `initialize_client`, then request `WaveFormat::new(32, 32, Float, actual_rate, 1, None)` with `autoconvert: true`. They never query the client mix/format after `initialize_client`, never check block align / channels on the capture client, and decode with `while byte_q.len() >= 4 { f32::from_le_bytes(...) }`. Next iteration **`byte_q.clear()`**, so a non-multiple-of-4 read permanently shifts the stream. `actual_channels` is only logged. macOS assumes the native ring is already f32 mono at `out_sample_rate` (0 falls back only in PTT, not in the live workers).
- **Rationale:** If AUTOCONVERT is ignored or the engine still delivers stereo interleaved float (or 16-bit PCM), samples are interpreted as mono f32: **2× speed**, garbage, or NaNs, while timestamps still advance in wall-clock — WAV padding then explodes. `actual_rate == 0` makes Windows `chunk_samples_target = 0` and macOS live `ratio = 0` → `resample_and_quantise` returns empty and **all audio is dropped**. Using `min_period` as `buffer_duration_hns` can also fail or glitch on some devices; that error becomes a 1 Hz reopen loop rather than a format retry.
- **Verification Method:** After `initialize_client`, log/read back mix format (channels, bps, rate) and compare to `desired`. Force a stereo mix without autoconvert in a mock and confirm chipmunk/garbage. Feed `byte_q` a length of `4k+2` twice and inspect decoded f32. Start capture on a device that reports 0 Hz (or stub `get_samplespersec`).

### 8. Last sub-chunk is discarded; loopback gaps are padded only in WAV, not in STT
- **Finding / Hypothesis:** Live loops emit only when `f32_buf`/`accum >= native_rate/5`. On stop/recover they `stop_stream` and drop the remainder (<200 ms). WASAPI loopback delivers **no events** while nothing renders; STT simply sees no chunks. The recorder reconstructs silence via `plan_pad` (capped at 10 min/gap and 30 min/session).
- **Rationale:** End of meeting / recovery loses up to 200 ms per source. Long mute/pause is correct in the WAV until the pad budget is exhausted, then diarization offsets lie. STT/VAD never sees the padded zeros, so transcript timestamps vs `system.wav` diverge after cap. Two sources with independent idle patterns get independent skew.
- **Verification Method:** Record a session that ends mid-utterance; compare last WAV samples to last STT chunk. Idle loopback for 15 minutes then speak; inspect pad vs `MAX_PAD_SAMPLES` and transcript `timestamp_ms` vs WAV offset. Idle for 2 hours and confirm skew banner / short WAV.

### 9. Capture `start_capture` can report success with no audio (Windows)
- **Finding / Hypothesis:** `capture_with_recovery` **always returns `Ok(())`** after the stop loop. Device-not-found and WASAPI errors are retried internally. `start_capture` therefore returns a live `Receiver` + `CaptureHandle` even when both names are wrong. Combined with duplicate-name selection and the wait-loop hang, the UI can show “capturing” while both threads are in 1 s error sleep or 250 ms event wait.
- **Rationale:** Opposite of macOS mic permission (terminal, logged, system-only continue). A meeting with a stale pinned BT name is a silent no-op until someone reads logs.
- **Verification Method:** `start_capture(Some("no-such-mic"), Some("no-such-out"))` on Windows; assert API success, zero chunks for 10 s, and recovery log spam. Compare macOS behavior with denied mic TCC.
