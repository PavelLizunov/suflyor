### 1. Tile / Ask Generation Mismatches
- **Finding / Hypothesis:** `GenGatedEvents::emit` in `tile_controller.rs` is a check-then-act race, not a generation lock. It loads `stream_gen` **outside** `current_streaming`, then calls `inner.emit` → `OverlayBarBridge::handle_ai_event`, which mutates/takes the **current** slot. `install_streaming_tile` bumps `stream_gen` and swaps the slot under a **different** critical section. A cancelled F9/follow-up/regenerate chunk (especially `Done`/`Error`) can still land on the newer tile. PTT is a second writer: `PttStreamSink` is intentionally **not** generation-gated and **not** stored in `ai_task`, so F9 abort / `session:stopped` cannot stop it. Rapid F9 always `TileWindow::new()`s another window; the old one is only labelled `"ai · superseded"` (and only if `old.convo_id != new_convo`).
- **Rationale:** The comment on `GenGatedEvents` claims it “closes the wrong-tile race that `JoinHandle::abort` alone leaves open.” Abort + a non-atomic gen check does not. Interleaving:
  1. Stale stream: `my_gen == current` is true.
  2. UI thread: `install_streaming_tile` (`fetch_add` + `slot.take()` + insert new `StreamingTile`).
  3. Stale `emit` runs `handle_ai_event`.
  - `Delta`: `push_str` onto the **new** `accumulated` (mixed answer).
  - `Done`/`Error`: `slot.take()` **steals the new tile**, renders the stale terminal state, `store_conversation` under the **new** `convo_id`, `followup_busy=false`. The real stream then has no slot (deltas dropped; its `Done` is a no-op).
  Same-tile dual-write: PTT streams via `PttStreamSink` while follow-up/regenerate uses the shared slot (`fire_followup_ask` / `fire_regenerate` → `install_streaming_tile`). `TILE_STREAMS` in `tile_window.rs` explicitly does **not** abort streaming F9/PTT/follow-up on close. Closing a live F9 tile drops the convo, but a later `Done` **re-inserts** it (`store_conversation` after `drop_conversation`). Rapid F9/PTT therefore stacks live windows (duplicates), and superseded/closed tiles can still receive GPU work.
- **Verification Method:** Instrument `GenGatedEvents::emit` and `handle_ai_event` with `(my_gen, current, convo_id, evt)`. Hammer F9 while tokens are in flight (and F9 vs in-tile follow-up / 🔄). Assert no `Delta`/`Done` with `my_gen < current` mutates the new slot. Second: start PTT, then F9 before PTT `Done`; confirm PTT still `set_blocks` on the PTT window and F9 `reset_ai_in_flight` does not orphan PTT’s pulse accounting. Third: close the F9 tile mid-stream; on `Done`, assert `conversations` does not resurrect that `convo_id`.

### 2. Incremental Markdown Parsing
- **Finding / Hypothesis:** `markdown.rs` is **not** incremental. `to_md_blocks_streaming` → `parse_streaming` → `parse` → full `pulldown-cmark` `parse_single_pass` on the entire prefix every ~50ms (`last_tile_render` / PTT `last_render`). There is **no** AST node cap, **no** `list_depth` cap, **no** block-count cap. Nested lists do `"  ".repeat(list_depth - 1)` on `Start(Item)`. Tables grow `table_rows` unbounded (only cell width is capped at 28). `stable_streaming_prefix` only hides an unfinished TeX tail; it does not bound work.
- **Rationale:** pulldown-cmark is event-based (not a retained tree), so you do not leak a growing AST across calls — but each call allocates a new `Vec<Block>` plus per-block `text`/`display_text` clones, and the tile rebuilds a `VecModel` from that. That is O(n²) CPU/alloc over a stream (their own ignored `parse_streaming_cost` bench). Adversarial token streams:
  - Deep CommonMark lists (`-` + 4-space indent, or many `Start(List)`): indent strings and Slint rows explode with input size (`list_depth` is a raw `usize`).
  - Thousands of tiny paragraphs / bullets / 1-row tables: unbounded `out` / `table_rows`, UI relayout can hitch or OOM before `AI_STREAM_MAX_TOKENS` feels “small.”
  - Unclosed fence: rest of the answer becomes one huge `CODE` block (survives, but one multi-megabyte `SharedString` can stall Skia).
  HTML/images are dropped (good for XSS in Slint). Private-use wrappers `\u{e000}`/`\u{e001}` for inline code mean a model that emits those codepoints can corrupt `display_text`. Deep nesting is unlikely to **stack-overflow** the parser (iterative events), but it **can** blow memory and freeze the UI thread that `invoke_from_event_loop` must run on — which then delays gating/supersede as well.
- **Verification Method:** Feed `parse_streaming` a 32k-char payload of (a) 4-space-indented nested lists to depth ≥ 64, (b) `"a\n\n"` × N paragraphs, (c) an unclosed ` ``` ` plus 100k of text. Measure `blocks.len()`, peak RSS, and time. Then stream the same via a fake `ai:event` Delta every 5ms with the 50ms throttle and watch TileWindow frame time. Add a hard cap (max blocks / max list_depth / max source bytes) and a test that adversarial input hits the cap instead of growing.

### 3. Unhandled Stream Termination
- **Finding / Hypothesis:** Terminal UI recovery is **event-dependent**. `followup_busy=false` and `"ai · done|error|прервано"` only run on `AiEvent::Done` / `Error` (`handle_ai_event`, `PttStreamSink`) or `session:stopped` **for the shared slot**. A mid-stream socket drop that yields neither event leaves the tile in `"ai · asking…"` / `followup_busy=true`. Several paths already drop without those events: `show_mlx_runtime_error` + `return` in `fire_f9_ask` / `fire_followup_ask` / `fire_regenerate` **after** `install_streaming_tile`; PTT MLX/STT failures; PTT is not on `ai_task` and is ignored by `session:stopped`. `ptt_tile_error` never clears `followup_busy`.
- **Rationale:** Authors already know abort emits no `Done`/`Error` (`install_streaming_tile` / `reset_ai_in_flight` comments). They patched **supersede** and **session stop** for the single F9 slot, not hang-up, worker-early-return, or PTT. Failure scenarios:
  - TCP reset / llama crash / channel drop inside `ask_stream_loop` (not in this diff): if the loop returns without `Error`, F9 spinner is permanent until a later F9 steals the slot; PTT spinner is permanent **forever** (no slot, no watchdog — the 30s watchdog only covers mic record).
  - F9 MLX resolve fail after placeholder + `followup_busy=true`: worker returns; slot still occupied; input dead until another ask.
  - PTT STT silence/error: `ptt_tile_error` paints a message but leaves `followup_busy=true` (set at tile creation) → follow-up/🎤/🔄 gated dead.
  - `let _ = slint::invoke_from_event_loop(...)` swallows a failed hop; even a real `Error` can miss the UI.
  - `dec_ai_in_flight` never runs → bar pulse stuck ON until `install_streaming_tile`/`session:stopped` (PTT never gets the latter).
- **Verification Method:** Mock `stream_chat_endpoint` to (1) close the rx with no terminal event, (2) return a transport error string, (3) hang. For each of F9, follow-up, PTT: assert within T seconds `followup_busy==false`, source_label is an error/interrupted string, and `ai_in_flight==0`. Force `resolve_route_endpoint` `Err` after `install_streaming_tile`. Call `ptt_tile_error` and assert `get_followup_busy()==false`. Kill the session during PTT and confirm the PTT tile is finalized the same way F9 is in the `session:stopped` arm.

### 4. Clipboard & Copy Safety
- **Finding / Hypothesis:** Visible tile copy (`wire_code_copy` / block `text`) is raw markdown of **rendered** body, not HTML — low XSS risk in Slint. The leak surface is `wire_copy(&tile, convo_id, bridge)` plus `ConvoState.messages`. On `Done`, both `handle_ai_event` and `PttStreamSink` store the **full send array** (`request_messages` + assistant), which for F9/PTT starts with `ai::build_request`’s **system** turn (`meeting_context`, approved memory from `context_for_meeting`, language/format directives, transcript scaffold). `reframe_for_send` is send-time only; stored history is original. `user_turn_markdown` only wraps the user question in a `~user` fence. `strip_followup_directives` implies copy once walked messages that contained internal markers. Code-block copy uses `Block.text` (raw), not `display_text`.
- **Rationale:** If whole-tile copy concatenates `ConvoState.messages` (it is given `bridge` + `convo_id`, not just the VecModel), clipboard gets:
  - System prompt / ROLE profile / memory facts (“private memory markers”).
  - F9 transcript framing (`Помоги ответить:`, “answer the last transcript question”).
  - Possibly legacy `FOLLOWUP_DIRECTIVE` on old convos if strip is skipped on the copy path.
  If copy is only `rendered` / on-screen blocks, system/memory stay off the clipboard unless the **model echoes** them (still a prompt-injection leak). Per-block «⭐ В память» (`wire_block_capture`) persists whatever is in `text`, including echoed memory and `~~~user` fences. Error tiles are sanitized (`classify_ai_error`); copy of a healthy answer is the real leak. Closing a tile mid-stream then hitting `Done` re-stores that prompt-bearing `ConvoState` (finding 1), so a later copy/follow-up can still see it.
- **Verification Method:** After F9 with non-empty meeting memory, copy (a) a code block, (b) whole-tile copy, (c) ⭐ capture. Grep clipboard/memory for `Ты —`, `Профиль`, `FOLLOWUP`, `На основе последнего вопроса`, and known memory strings that never appeared on screen. Unit-test `wire_copy` to copy **only** `rendered` / non-system roles, and to run `strip_followup_directives` + drop `role=="system"`. Confirm regenerate/follow-up copy after `reframe_for_send` still cannot emit the send-time system blob (it must not have been stored).
