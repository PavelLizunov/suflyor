### 1. Slint ↔ Tokio deadlock: `blocking` UI hop while `Mutex<SlintRuntime>` is held
- **Finding / Hypothesis:** No path in `slint_session.rs` currently holds `lock(&rt)` across `events.emit` / `spawn_tile_full` (meeting-ending explicitly `drop(s)` before emit at `transcript_forwarder` ~meeting-ending block; rate-limit `drop(s)` before `"tile:rate-limited"`). Deadlock still exists **if** `SlintUiBridge` uses `slint::blocking_invoke_from_event_loop` **and** the UI closure re-enters `runtime_state::lock` (`runtime_state.rs` `lock()` → `Mutex::lock`). `start_session` is documented as UI-thread (`slint_session.rs` module docs) and itself calls `events.emit("cost:update")` / `"session:started"`; `blocking_invoke_from_event_loop` from the Slint thread deadlocks the event loop with itself.
- **Rationale:** Classic ABBA: tokio worker holds `std::sync::Mutex<SlintRuntime>` → blocking invoke → UI runs a chip handler that calls `lock(rt)` (pause, stop, mic mute, start). Non-blocking `invoke_from_event_loop` avoids the hard deadlock but converts it into unbounded UI-queue latency (finding 2).
- **Verification Method:** Temporary `blocking_invoke_from_event_loop` in `forward_event` that `lock(rt)` inside the closure; from a running session spam F6/auto-tile while clicking Pause/Stop on the bar. Watch for freeze with two threads in `pthread_mutex_lock` / `WaitForSingleObject` on the same `SharedSlintRuntime`. Also call `start_session` directly from a Slint callback if the bridge is blocking.

### 2. Hot-path contention: audio forwarder vs session start/stop vs QA eviction on one `std::sync::Mutex`
- **Finding / Hypothesis:** `forward_audio_chunks` (`slint_session.rs`) takes `lock(&rt)` on **every** `AudioChunk` (health stores, `collect_system_audio` which can `extend` up to `TARGET_SAMPLE_RATE * 30` i16s), then **again** after `stt_tx.reserve().await`. That mutex is the same one `start_session_inner` holds while `full_transcript.clear()` (cap 20_000), `qa_cache.clear()`, `journal.take()`+`drop(j)` **under the guard**, and the same one `maybe_spawn_auto_tile` holds for TTL `retain`, prefix `retain`, and half-eviction (`QA_CACHE_MAX_ENTRIES = 256` clone-all-keys + `sort_by_key` + remove) after the AI call.
- **Rationale:** Invariant “background must never lock the UI thread” is violated in spirit: the UI thread uses the same blocking `std::sync::Mutex`. A 30s PCM copy or 256-entry sort on a tokio worker stalls Pause/Stop/mic-mute/`start_session`. `drop(journal)` under the start-session lock can join a writer thread while audio is queued on the same mutex (stop_session correctly `drop(s)` before `j.shutdown(Duration::from_secs(3))` — start does not).
- **Verification Method:** `record_audio_enabled` + `begin_system_audio_collector` so the 30s vec is live; run a profiler (`mutex` contention / `tokio-console`) during capture. Force `qa_cache` to 256 (aggressive `auto_tile_every_line`) then trigger one more tile while dragging the bar. Measure Slint frame time vs `lock(&rt)` hold time. Add a debug `Instant` around the start_session first `{ let mut s = lock(&rt); ... }`.

### 3. Generation fence TOCTOU: post-AI `session_gen` check does not cover mutations
- **Finding / Hypothesis:** `maybe_spawn_auto_tile` captures `gen_for_tile = lock(&rt).session_gen` in `transcript_forwarder`, then only re-reads gen **after** `ai::complete_with_usage_endpoint` (`if lock(&rt).session_gen != session_gen { return; }`). There is **no** check at function entry. Before the AI await it already mutates `recent_tile_triggers`, `recent_question_prefixes`, and `qa_cache.retain`. After a successful check it **releases the lock** and then writes `qa_cache.insert`, `session_cost_microcents`, `last_question`/`last_answer`, journal, `cost:update`, `spawn_tile_full`.
- **Rationale:** Rapid Stop/Start bumps gen twice (`stop_session` and `start_session_inner` both `wrapping_add(1)`). Window: check passes (still old gen) → start clears cache / new session live → insert/bill/spawn land on the **new** session. Error path has the same hole around `last_ai_err_ms` / error tiles (partially commented as v0.8.2 M1, still not atomic with spawn).
- **Verification Method:** Hook `complete_with_usage_endpoint` with a 2s sleep. Start session A, trigger auto-tile, Stop+Start session B during the sleep. Assert B’s `qa_cache`, `session_cost_microcents`, `last_question`, and tile registry stay empty. Repeat with the sleep **after** the gen check (inject delay between check and `qa_cache.insert`).

### 4. Generation fence bypass: forwarder stamps work with the **post-stop** gen
- **Finding / Hypothesis:** `stop_session` bumps `session_gen` and `transcript_task.abort()` under the **same** guard. `JoinHandle::abort` only unwinds at `.await`. `transcript_forwarder` between `stt_rx.recv().await` and the next await still runs: `let gen_for_tile = lock(&rt).session_gen` now reads the **already bumped** gen, then `tokio::spawn(maybe_spawn_auto_tile(..., gen_for_tile))`. After Stop (no restart) the later `session_gen != session_gen` check **succeeds** and a tile/cost/cache write is applied to a stopped session. `health_task` has the same “one extra iteration after abort” behavior (`tick.tick().await` then `lock` + `spawn_tile_full` mic-down + `"health:update"`).
- **Rationale:** The fence is “gen changed during AI”, not “session still active”. Abort is not a generation fence. `ask_stream_loop` (`overlay-backend/src/runtime.rs`) has **zero** `session_gen` checks; in-flight `"ai:event"` already hopped to Slint can paint the next session’s in-flight tile.
- **Verification Method:** On a debug build, `std::thread::sleep` in `transcript_forwarder` after pause/mute checks, before `gen_for_tile`. Click Stop during the sleep. Confirm an auto-tile still spawns and `session_cost_microcents` moves. For F9: start stream, Stop/Start, confirm leftover `ai:event` deltas apply to the new overlay tile.

### 5. `AUTO_TILE_SINGLE_FLIGHT_STATE` does not stop in-flight work and can latch shut on wrap
- **Finding / Hypothesis:** `try_acquire_auto_tile` (`slint_session.rs`) packs `session_gen.wrapping_shl(1) | 1` into a process-wide `AtomicU64`. A **newer** gen is allowed to acquire while the old permit is still live (test `auto_tile_permit_is_single_flight_per_session` asserts supersede). Old `Drop` CAS fails harmlessly, so two AI calls run. `session_gen` is a full `u64` but the atomic only stores 63 bits; after `wrapping_add` rolls gen below `current >> 1`, `current_gen > session_gen` makes every acquire return `None` (MLX / `every_line` auto-tiles die for the process).
- **Rationale:** Single-flight is a cost/UI-flood valve, not a session fence. Combined with finding 3–4, superseded calls still mutate shared `SlintRuntime`. Wrap is academic for gen itself, not for the shifted atomic.
- **Verification Method:** Unit test already shows two overlapping permits. Add a test: set `AtomicU64` to `(u64::MAX << 1) | 0`, `try_acquire_auto_tile(&state, 0)` must not spin-fail forever. Integration: MLX + rapid restart while a 384-token call is in flight; count concurrent `AiRequest` journal events.

### 6. Task cleanup: aborted handles are not joined; several tasks are never tracked
- **Finding / Hypothesis:** `transcript_task` / `ai_task` / `health_task` are `take()` + `abort()` on start/stop; handles are **not** awaited. Untracked spawns: (1) `forward_audio_chunks`’s `tokio::spawn` — JoinHandle discarded; (2) per-line `tokio::spawn(maybe_spawn_auto_tile)` — up to ~9 min with retries, only gen-bail; (3) `tokio::task::spawn_blocking` for `drop(recorder)`; (4) `std::thread::spawn` archive indexer in `stop_session`; (5) `maybe_run_debrief` → `rt_handle.spawn(run_post_meeting_debrief)` with no handle and no gen; (6) `stt::spawn` pipeline never aborted/joined — `stt::reset_gigaam_cache()` runs while the old STT task may still be alive (`start_session_inner` after `drop(prior_capture)`).
- **Rationale:** Abort is cooperative; audio forwarder keeps `lock(&rt)` until `src_rx` closes (capture drop happens **after** the big start/stop critical section). Two forwarders can overlap on restart and bump `health.last_audio_frame_ms` / fill `system_audio_collector` for the **new** session. Journal is `clone()`d into the forwarder and every auto-tile; `stop_session`’s `j.shutdown(3s)` cannot drain while clones remain, so `SessionStop` can be followed by `DetectorDecision` / `AiRequest` / `AiResponse` from a zombie tile (or shutdown times out on the UI thread).
- **Verification Method:** `tokio-console` / task dump: after Stop, assert zero tasks named forwarder/health/auto-tile within N ms. Restart with GigaAM and TSAN/logging around `reset_gigaam_cache`. Hold a clone of `Journal` in a paused auto-tile and see whether `shutdown` returns durability error and whether post-stop journal events appear. Rapid start/stop 20× and check `SYSTEM_AUDIO_OWNER` + leaked `JoinHandle`/thread count.

### 7. UI-thread blocking (priority inversion, not a mutex cycle)
- **Finding / Hypothesis:** `start_session_inner` on the Slint thread does sync `stt::validate_gigaam_dir` (~0.5s), `audio::start_capture`, journal open, and the long first `lock(&rt)`. `stop_session` (if called from the bar) runs `j.shutdown(Duration::from_secs(3))` and may `std::thread::spawn` indexing but the shutdown itself is inline. Invariant “UI callbacks must NEVER block on async futures” is kept only by blocking **sync** instead; `tokio::spawn` from that thread still requires a runtime context — `Handle::block_on(start_session)` plus any worker `blocking_invoke_from_event_loop` is a hard deadlock.
- **Rationale:** Capture/WASAPI/TCC (`SYSTEM_AUDIO_SESSION_STUCK` on macOS pending) on the event loop stalls every `invoke_from_event_loop` already queued by transcript/health/AI. Workers then pile up on `lock(&rt)` (finding 2).
- **Verification Method:** Start session with invalid/slow GigaAM dir and a debugger break in `start_capture`; confirm the bar is frozen (not just a spinner). Stop a session with a stuck journal writer; confirm up to 3s UI stall. Audit `overlay_host` for `block_on` vs `runtime.enter()` around `start_session` / `stop_session`.

### 8. Stream / debrief / namer vs session identity
- **Finding / Hypothesis:** `ask_stream_loop` emits every `ai:event` then always `cost_apply` + `"cost:update"` if the task is **not** aborted at `ai_rx.recv().await`. `ai_task.abort()` on stop skips the tail (unwind), but deltas already forwarded through `SlintEvents` are unfenced. `run_post_meeting_debrief` / `run_meeting_summary` take a transcript snapshot (good) but spawn tiles with no `session_gen`; a debrief started from Stop can appear after the next Start. `crate::session_namer::maybe_spawn_namer` is invoked from the forwarder with only `&rt` (no gen stamp in this file).
- **Rationale:** `session_gen` was added for auto-tiles (E9) and never applied to F9/PTT streams, debrief, or namer writebacks (`session_name`, `session_name_inflight`). Rapid stop/restart pollutes bar title, cost chip, and in-flight tile text.
- **Verification Method:** F9 stream a long answer; Stop/Start mid-tokens; assert new session cost is 0 and no further `ai:event` mutates the new tile. Stop with debrief enabled, Start immediately; assert debrief tile does not bind to the new `current_session_id`. Log `session_name` across restart with namer delay.

**Net:** The code avoids `MutexGuard` across `.await` and usually drops `lock(&rt)` before UI hops — that is the right shape. The remaining failures are (a) one global `std::sync::Mutex` on the audio tick, (b) `session_gen` used as a stale snapshot rather than a held epoch, (c) `abort()` treated as join, (d) untracked forwarder/auto-tile/STT/debrief tasks keeping `Journal`/`SlintRuntime` alive past Stop.
