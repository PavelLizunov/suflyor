### 1. Stealth Leakage — WDA is not a gate on first on-screen frame
- **Finding / Hypothesis:** `present_window_stealth_aware_at` (`window_lifecycle.rs`, `do_reveal` closure) always parks, `show()`s, then on HWND grab runs `decorate(hwnd)` → optional `apply_stealth_one` → **unconditional** `move_window_pos_only`. `apply_stealth_one` only logs `set_stealth` failure and does not inhibit reveal. Contrast `open_tray_menu` in `bar_tray.rs`, which treats `set_stealth` `Err` as `return false` and whose fallback **hides** the menu.
- **Rationale:** Stealth is a best-effort paint afterthought for Settings / palette / wizard / help / tiles / transcript / archive. If `SetWindowDisplayAffinity` fails (layered/winit HWND, RDP, affinity readback mismatch in `win32.rs::set_stealth`), the first **on-screen** frame is capturable while `STEALTH_ON` remains true and the bar chip can still show effective-on (`STEALTH_EFFECTIVE` is bar-only; comment at `STEALTH_EFFECTIVE` admits this). Screen-share leakage of the “most sensitive surface” (transcript) is exactly the bug class this registry was written to kill.
- **Verification Method:** Force `set_stealth` to fail (shim readback mismatch). Open Settings and a tile with stealth enabled; capture with Win+Shift+S / Teams share. Confirm tray menu stays hidden/off-screen on the same failure, Settings does not.

### 2. Stealth Leakage — `show()` + HWND realization vs parking race
- **Finding / Hypothesis:** Parking is `set_platform_window_position(..., -32000, -32000)` then `win.show()` (`present_window_stealth_aware_at`), with WDA deferred until `realize_with_retries` (`HWND_REVEAL_FAST_MS` → 80ms → `HWND_GRAB_DELAY_MS * 2`). `grab_hwnd` docs in `win32.rs` state the native HWND does not exist until after an event-loop tick; winit commonly **maps at default monitor placement first**, then applies the pending Slint position.
- **Rationale:** `-32000` only helps if it is committed atomically with `WS_VISIBLE`. If winit/DWM presents even one frame at the default (primary-center) location, that frame has **no** `WDA_EXCLUDEFROMCAPTURE`. This is the exact cold-start flash Поток C claimed to close. Off-screen parking also does not help DXGI/GDI paths that enumerate `WS_VISIBLE` windows (the F8 path already documents GDI ignoring WDA).
- **Verification Method:** Enable stealth, start under a running `Windows.Graphics.Capture` / Teams share. Slow the UI thread (heavy Settings theme). Record the first 200ms with a capture that includes the primary output. Also log `GetWindowRect` immediately inside the first `WM_SHOWWINDOW` (temporary subclass) to see if origin is ever on a real `rcMonitor` before WDA.

### 3. Stealth Leakage — bar fallback deliberately un-stealths the control surface
- **Finding / Hypothesis:** `apply_overlay_hwnd` fallback (`bar_tray.rs`) calls `set_global_stealth_effective(false)` then `set_platform_window_position` onto the primary **even when `global_stealth()` is true**, because “the bar is the whole control surface”. Aux fallback (`present_window_stealth_aware_at`) at least keeps the window parked under stealth.
- **Rationale:** Honest chip state does not stop pixels. A slow first-realize (the case retries exist for) is also the case most likely to miss WDA. The bar is the session/transcript chrome; leaking it “because UX” reintroduces the original screen-share flash on the path that was supposed to be I3-safe.
- **Verification Method:** Block `HasWindowHandle` until after the last retry (or delay winit realize). Boot with stealth on and a share already running. Confirm the bar appears in the share with the amber “stealth unavailable” pill — i.e. the UI tells the truth while still leaking.

### 4. Stealth Leakage — live toggle does not cover all HWNDs; tray menu is a ghost
- **Finding / Hypothesis:** `WindowRegistry::apply_stealth` walks tiles, settings, palette, text_ask, wizard, help, recover_offer, transcript, archive, lock_menu. It does **not** include `TrayMenuWindow`. `open_tray_menu` applies WDA only at realize. Bar is a separate `apply_bar_stealth` call the caller must remember. Capture overlay is explicitly excluded.
- **Rationale:** Registry was sold as “ONE path instead of three hand-maintained loops” after Help/recover-offer leaked. The tray menu is a new fourth loop: open while stealth is off, then toggle stealth on (Settings/bar/wizard) → menu stays capturable. Any future popup that does not go through `present_window_stealth_aware` + registry insert repeats FIX #6.
- **Verification Method:** Stealth off → right-click tray → turn stealth on from Settings (menu still open) → share screen. Repeat with lock-mode menu vs tray menu and compare `GetWindowDisplayAffinity`.

### 5. Stealth Leakage — `set_skip_taskbar` can unhide a tray-hidden bar and flash style bits
- **Finding / Hypothesis:** `set_skip_taskbar` (`win32.rs`) does `ShowWindow(SW_HIDE)` → restyle → `ShowWindow(SW_SHOWNOACTIVATE)` + `HWND_TOPMOST` whenever TOOLWINDOW/APPWINDOW bits change. `apply_bar_stealth` always calls it. `hide_bar_to_tray` only `hide()` + `force_hide` and sets `BAR_TRAY_HIDDEN`; it does not stop stealth applies.
- **Rationale:** A winit re-show that drops `WS_EX_TOOLWINDOW` (the I2 scenario the tests encode) makes the next stealth toggle a **show**. That restores a tray-hidden bar into a share, and the hide/show pair is a documented compositor flash. `skip_taskbar_exstyle` ignores the `skip` argument and always forces TOOLWINDOW, so the *second* call is idempotent — the *first* mismatch is the dangerous one.
- **Verification Method:** Hide bar to tray. Force exstyle without TOOLWINDOW (or restart winit window). Toggle stealth. Observe bar reappearing and a one-frame opaque/black flash. Confirm `BAR_TRAY_HIDDEN` still true (state/UI desync).

### 6. Multi-Monitor Geometry — first pin uses possibly unset size (1×1 / half-off primary)
- **Finding / Hypothesis:** `apply_overlay_hwnd` pins with `get_window_rect(hwnd).map(|(_,_,_,w)| w).unwrap_or(0)` as soon as `grab_hwnd` succeeds. `present_window_stealth_aware_at` uses `get_window_rect(...).unwrap_or((0,0,460,360))` — **error** fallback only; a real `0×0` or `1×1` rect is trusted. `recenter_when_sized` exists for compact resize and waits for width, but the initial realize path does not share that wait.
- **Rationale:** Slint applies `set_size` on a later tick. A realized HWND with default min size gets centered as a sliver, or with `bar_w == 0` is placed at `primary.left + width/2` so a later 1280px layout extends off the right edge. On a 1200px-wide portrait **primary**, a 1280 logical bar cannot fit (`pick_monitor` is not used for the bar; it is forced to primary). Mixed DPI: parked at `-32000`, the window may inherit the nearest monitor’s scale; `PhysicalPosition` then moves that pixel size onto a different DPI output → overflow or visual 1×1 until a later layout.
- **Verification Method:** Primary portrait 1200×1920 + landscape 1920×1080. Cold start full bar; screenshot. Repeat with primary 175% / secondary 100%, stealth on (longer park). Log `GetWindowRect` at first successful `grab_hwnd` vs 200ms later. Toggle compact (`apply_bar_size`) and confirm only that path recenters.

### 7. Multi-Monitor Geometry — `pick_monitor` and pin packing fail closed into wrong/empty space
- **Finding / Hypothesis:** `pick_monitor` (`win32.rs`) is `monitors.iter().find(|m| m.is_primary).copied()?` — **no primary ⇒ `None`**. Callers then use `(100,100)` or `(60,24)`, which need not lie on any `rcMonitor` (negative-origin virtual desktop; owner layout has portrait at `x=-1200`). `TILE_MONITOR_PIN` packs `(left << 32) | (top as u32)` with sentinel `i64::MIN`; `left == i32::MIN && top == 0` collides with AUTO. Pin match is top-left of `rcMonitor` only; a driver that reports a 1px origin shift after sleep looks like “unplugged” and silently falls back.
- **Rationale:** “Never an off-screen tile” is false if `enum_monitors` is empty/transient (display mode change) or primary bit missing (some virtual adapters). `(100,100)` on a desktop whose origin is `(-3840,-2160)` is not on a display. Saved-pos validation (`pos_on_visible_monitor`) only tests the **origin** with 8px slack, and uses `pos < right - 8`, so a window flush to the right edge is treated as stale and recentered — while a window whose origin is on-screen but whose body is entirely on the gap below a landscape primary (`(300,1300)` in the unit test) is rejected (good) yet a 2000px-wide window at `(0,0)` is accepted (overflow).
- **Verification Method:** Unit-test `pick_monitor` with all `is_primary: false`, empty slice, and portrait-only. Pack `set_global_tile_monitor(Some((i32::MIN, 0)))` and read back. Plug/unplug the pinned monitor; spawn tiles. Place a window at `right - 4` and reopen via `present_window_stealth_aware_at` with `saved_pos`.

### 8. DWM Transparency & Paint Races — hide/restyle/show and blur-behind are not ordered with first paint
- **Finding / Hypothesis:** `apply_transparency` (`win32.rs`) calls `set_skip_taskbar` (hide/show), then `SetWindowLongPtr(GWL_EXSTYLE)`, then `DwmExtendFrameIntoClientArea(margins=-1)`, then `DwmEnableBlurBehindWindow` with `CreateRectRgn(0,0,-1,-1)`. Bar uses `make_transparent_overlay` (sets `WS_EX_TRANSPARENT`). Tiles use `make_transparent_tile` (clears it). No `WS_EX_LAYERED` / `SetLayeredWindowAttributes` is applied here; per-pixel alpha is entirely DWM composition (`composition_enabled()`).
- **Rationale:** Frame extension into the client area makes the HWND **black glass** until Slint produces an alpha frame. That is safe only while parked. Any path that decorates after the window is mapped (live stealth toggle, `reveal_window` after F8 `hide_own_windows`, tray restore `show_windows`) produces a black flash and a frame of lost alpha. If DWM composition is off, the same margins render **opaque black** with no fallback fill. `WS_EX_TRANSPARENT` on the bar is the same class of bug Phase E6 already shipped on tiles (“тайлы нельзя двигать”): hit-testing is disabled at the OS level, so chips only work if winit later clears the bit — a race the debug `eprintln` was written to catch, then compiled out of release.
- **Verification Method:** RDP or disable DWM composition; confirm bar/tiles go black/opaque. On a local Win11 box, spy `GWL_EXSTYLE` after 0/1/10 frames for bar vs tile (`WS_EX_TRANSPARENT` 0x20). Toggle stealth on a visible Settings window; camera-record the chrome for a black/square-corner frame. Click bar chips immediately after realize; if clicks fall through, the overlay style stuck.

### 9. DWM Transparency — click-through and topmost are not re-asserted coherently
- **Finding / Hypothesis:** `set_skip_taskbar` re-asserts `HWND_TOPMOST` but does not re-run `apply_transparency`. `show_windows` restores topmost only if the hide snapshot said so. `make_transparent_overlay` is one-shot in `apply_overlay_hwnd`. Slint `no-frame` still leaves caption bits that they strip once via `GWL_STYLE`; a later winit style refresh can bring back ghost caption buttons **and** `WS_EX_APPWINDOW`.
- **Rationale:** Click-through failures after drag were already a production incident (`drag_begin` comments: modal `WM_NCLBUTTONDOWN` stuck TouchArea). A compositor restyle that re-ORs `WS_EX_TRANSPARENT` onto tiles recreates unclickable tiles; one that clears it on the bar makes empty pixels steal clicks from Zoom/Teams underneath — the overlay’s whole purpose.
- **Verification Method:** After F8 capture hide/show, after tray hide/restore, and after compact resize, dump `GWL_EXSTYLE`/`GWL_STYLE` and click: (a) bar empty glass, (b) bar chips, (c) tile pin/close, (d) window below the bar. Confirm whether caption glyphs return (`SWP_FRAMECHANGED` path).

### 10. Window Destruction — registry unhook is convention-only; native subclass is never removed
- **Finding / Hypothesis:** `WindowRegistry` is `Clone` of `Rc<RefCell<Option<…>>>` slots plus `TileWindows`. This module has `apply_stealth` / `apply_scheme` / `refresh_open_tiles` (`tiles.retain` is only mentioned in comments) and **no** close/Drop path. `install_stealth_cursor_guard` (`win32.rs`) `SetWindowSubclass`s forever; `set_stealth` ignores reinstall failure. `DRAG_ANCHOR` is a process thread-local not tied to HWND lifetime.
- **Rationale:** If a close handler `hide()`s but leaves `Some(window)` in the slot, `apply_stealth` will `grab_hwnd` a hidden or already-destroyed HWND. HWND value reuse then applies WDA / skip-taskbar / `ShowWindow` to a foreign window. Conversely, dropping the Slint component without `force_hide` leaves secondary-monitor pixels (the bug `force_hide` exists for). Subclass + `SetTimer(..., 1ms)` on a stealthed HWND that is hidden rather than destroyed keeps waking the UI thread; after destroy, a stale subclass proc is a UAF if removal races the last `WM_TIMER`. Tray menu dismiss sets `hide()` but is outside the registry, so a subsequent global stealth walk cannot even see it to unhook.
- **Verification Method:** Open/close Settings, Help, transcript, archive, 20 tiles, lock menu, tray menu in a loop while toggling stealth and scheme. After each close, assert the corresponding `Option` is `None` / tile vec length matches `open-tiles`, `grab_hwnd` fails, and Spy++ has no leftover TOOLWINDOW. Enable stealth so the cursor subclass installs; close the window and confirm no `WM_TIMER` 0x55F1_0002 and no `stealth_cursor_subclass_proc` hits. Mid-drag close a tile; confirm `drag_update` is a no-op (`drag_end`).

### 11. Cross-cutting — “effective stealth” is an unreliable invariant
- **Finding / Hypothesis:** `set_global_stealth` stores intent ∧ `stealth_supported()` (`true` **const** on Windows, `false` on macOS). `set_global_stealth_effective` stores bar apply+readback only. `apply_stealth_one` does not update any aggregate. `stealth_supported()` does not check build 2004 / `SetWindowDisplayAffinity` capability.
- **Rationale:** Every realize path reads `global_stealth()` (intent), not `global_stealth_effective()`. New windows will attempt WDA because the user asked, then appear anyway on failure (Finding 1). The Settings status line / Diagnostics row / 🎯 chip can read ON while a tile, palette, or tray menu is capturable. That is not a residual limitation; it is a broken invariant for an anti-capture product.
- **Verification Method:** Fail WDA on tiles only (bar succeeds). Inspect chip, Settings stealth tab, and a Teams share of the tile. Repeat on a Windows 10 1909 VM where affinity APIs fail but `stealth_supported()` still returns true.
