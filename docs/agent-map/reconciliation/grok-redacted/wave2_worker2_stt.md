### 1. Task Queue & Memory Bounds
- **Finding / Hypothesis:** `overlay-backend/src/stt.rs` `spawn()` creates an output channel of 64 (`mpsc::channel::<TranscriptEvent>(64)`) and a concurrency cap of 6 (`Semaphore::new(6)`), but **every flush does `tokio::spawn` first and only then `sem.acquire_owned().await`**. The VAD loop never waits on that semaphore. Cloud/local HTTP and GigaAM both copy this pattern. The in-loop `Utterance` buffers are capped (~10 s/source), but **in-flight work is not**: each spawned task owns the PCM (`to_send.samples` / `samples`) until a permit is granted. Authors even documented the failure mode in the GigaAM spawn (`~800KB` per queued task if inference is slower than flush) and then implemented the anti-pattern that causes it.
- **Rationale:** The semaphore bounds *execution*, not *admission*. The VAD task keeps `audio_rx.recv().await` flowing while STT is stuck, so the real queue is the Tokio task set. Failure sequence in a multi-hour meeting: Groq/whisper-server hangs or falls behind → 6 permits held for the full retry budget → flushes continue (2 sources × silence hang 800 ms or 10 s size cap) → N tasks sit on `acquire_owned`, each retaining ~10 s of 16 kHz i16 (~320 KiB, plus later WAV/f32 copies). A 2 h call at ~1 utterance/2 s/source is O(10³) tasks and **O(1–2+ GiB) of unconsumed PCM** with no drop-oldest, no max-depth, no backpressure into capture. Secondary leak: `finish_transcript` does `tx.send(...).await` on a 64-deep channel; a slow UI blocks workers *while they still hold permits*, which accelerates spawn-side buildup rather than shedding load. `transcribe_once()` (PTT/ad-hoc) bypasses the semaphore entirely, so a live session + one-shot can stack more buffers/requests on the same process. Shutdown path `Err(_) => return` on a closed semaphore **silently drops speech**.
- **Verification Method:** Unit/integration: replace `transcribe` with a 30–90 s sleep; drive `audio_rx` with two sources of voiced 200 ms chunks for 10–30 minutes; assert `JoinHandle` count and process RSS stay bounded (they will not). Probe: wrap the semaphore with a metrics gauge (`available_permits`, `spawned_not_started`) or fail the test if `tokio::runtime::Handle::metrics().spawned_tasks_count()` grows linearly with meeting length. Fix shape to verify against: **acquire (or `try_acquire`) on the VAD task before `spawn`**, plus a hard cap (e.g. bounded `mpsc` of size 6+K with drop-oldest). Confirm `transcribe_once` shares the same limiter.

### 2. Timeout Cascades & Network Drops
- **Finding / Hypothesis:** Live HTTP STT uses a process-wide `reqwest::Client` with **`.timeout(Duration::from_secs(30))`**. `transcribe()` retries **3 times** with backoff 0 s / 1 s / 2 s while **holding the semaphore permit**. `is_permanent_error()` only short-circuits on substring `HTTP 401|403|404|413`. Transport failures become generic `"STT network error"` (retryable). **There is no circuit breaker, consecutive-failure budget, `Retry-After` handling, or jitter.** Ad-hoc `transcribe_once` uses a **60 s** client timeout (inconsistent with live 30 s). Health (`last_stt_ok_ms`) is write-only on success and never used to shed STT load.
- **Rationale:** Worst case per utterance: 30+1+30+2+30 ≈ **93 s** occupying one of six slots. Offline/captive-portal/DNS-dead: every flush still hammers the endpoint three times; with finding (1), the waiter queue grows for the whole meeting. 429 is explicitly classified retryable, but 1–2 s backoff will **amplify** rate limits (six concurrent waiters wake almost together — no jitter). A single slow Groq (not fully hung) turns the pipeline into ~6/93 utterances/s while VAD continues at real-time, so transcript latency cascades from seconds to minutes and never recovers until the network does. Session stop does not cancel in-flight POSTs; late `TranscriptEvent`s can still `send` if `rx` is alive (ghost lines after hangup) or are dropped if not. Permanent-error matching is brittle (`"STT HTTP {status}"` Display form) — a redaction/format change would re-enable auth hammering (tests currently pin the string).
- **Verification Method:** Point `SttBackendCfg::Whisper { base_url }` at a blackhole (`127.0.0.1:1`) and at a listener that accepts TCP then stalls; measure wall time per `transcribe` (~93 s) and request count (×3 per utterance). Add a 429 stub with `Retry-After: 30` and show retries at 1 s/2 s. Inject 10 consecutive failures and show the 11th still fires (no breaker). Chaos: `iptables`/disable NIC mid-meeting and watch RSS + log spam. Assert a breaker (e.g. after N failures open for T seconds, fail-fast, stop spawning) and that live vs `transcribe_once` timeouts match.

### 3. ONNX / GigaAM Runtime Hangs
- **Finding / Hypothesis:** GigaAM inference is `spawn_blocking` → `gigaam_transcribe` → **`std::sync::Mutex` on a process-global cached model** → `transcribe_f32` with **no timeout, watchdog, or isolation**. Mutex poison is recovered (`into_inner`), which only helps panics, not deadlocks. `GIGAAM_CACHE` / `shared_gigaam_model()` serialize live + PTT on one ORT session. `validate_gigaam_dir()` loads that cache **synchronously on the UI/session-start thread**. If GigaAM was selected but `shared_gigaam_model` fails inside `spawn()`, `gigaam = None` and `http_target = None` — **all subsequent speech is dropped with no cloud fallback** (only a load-time error log).
- **Rationale:** One wedged `transcribe_f32` holds the model mutex forever. Up to six permitted tasks can sit in `spawn_blocking` (one in ORT, five on `Mutex::lock`); remaining flushes keep spawning (finding 1). Result: **one stalled utterance wedges the entire meeting transcript** for the local backend. `tokio::time::timeout` around `spawn_blocking` would **not** unwedge this: dropping the `JoinHandle` does not abort the blocking thread or drop the mutex guard. Diarization already isolates sherpa ORT in a sidecar because “sherpa's onnxruntime can't share ours”; live GigaAM did not get the same treatment. Extra: `configure_gigaam_accelerator` is a process-global ORT preference that must be set before load; a mid-session `reset_gigaam_cache()` + reload under a different accelerator can race in-flight `Arc<Mutex<Model>>` users. UI hitch: `validate_gigaam_dir` blocks the calling thread for a full ORT session build (comment claims ~0.5 s; a bad GPU EP can be much longer or hang).
- **Verification Method:** Test double/`#[cfg(test)]` hook that parks inside `transcribe_f32` (or a custom EP that deadlocks). Start a meeting, flush two utterances, confirm the second never emits `TranscriptEvent` and `last_stt_ok_ms` freezes while `last_audio_frame_ms` still advances. Thread dump should show one blocking thread in ORT and others in `Mutex`. Negative test: GigaAM load `Err` → voiced buffers pass the noise gate and produce **zero** HTTP/GigaAM submits. Hardening to verify: sidecar or watchdog process (mirroring `diarize.rs`), fail the utterance after N seconds **and** isolate the session so the mutex cannot pin the rest of the call; fallback to cloud on load failure.

### 4. Diarization Coordination
- **Finding / Hypothesis:** `run_diarization` (`diarize.rs`) is a **blocking worker** that reads `system.wav` and `Command::output()`s `suflyor-tts diarize` with **no timeout, no kill, no memory cap beyond a 3 h header guard** (`MAX_DIAR_SECS = 3 * 60 * 60`). Auto mode runs the sidecar **sequentially for N=2..=6** (early-stop via `consider_auto_candidate`). Alignment (`system_windows` / `align_all` / `align_all_speakers`) owns each SYSTEM line from `audio_ms` to next SYSTEM start, **capped at `WINDOW_CAP_MS` (30 s)**. This module does **not** check that capture has finished or that the recorder still has the WAV open. Install path (`diar_install.rs`) is crash-safe (sentinel + staging) and single-flight (`INSTALL_BUSY`), but that does not serialize **live GigaAM ∩ archive diarization**.
- **Rationale:** Hang: sidecar ONNX deadlock → worker blocked forever on `output()`; UI progress is only updated *before* each pass, so a 3 h file can look frozen on “Определение говорящих…” with no abort. Memory: comments admit 1 h ≈ 230 MB f32; **3 h ≈ 690 MB waveform plus models**, and auto mode can do that up to five times. Capture conflict: on Windows, a still-open recorder handle can make sidecar open fail or parse a torn WAV; `guard_wav_len` is a header-only duration read and will not see a file still growing. Timeline breakage: (a) `align_all` collapses a 10 s forced-flush STT block to the **dominant** speaker — overlapping speech inside one VAD utterance is hidden unless the UI uses `align_all_speakers`; (b) phantom filter drops clusters that do not overlap SYSTEM windows — missed STT or `audio_ms` skew (legacy unpadded recordings; `timeline_reliable` only warns) **deletes real speakers** and renumbers survivors, so labels jump; (c) windows ignore MIC lines, so a remote/local mix only diarizes loopback; (d) live GigaAM (hundreds of MiB ORT, DirectML/CoreML) + sidecar diarize of a long archive compete for GPU/RAM — the isolation comment solves ABI sharing, not resource coupling, and can stall or OOM the meeting. `friendly_error` redacts paths for UI; `bail!("diarization failed: {}", stderr)` can still log filesystem paths.
- **Verification Method:** Hang: stub `suflyor-tts` that ignores SIGTERM and sleeps; call `run_diarization` and show the worker never returns (add a test seam around `run_sidecar` with a timeout+kill). In-progress session: start capture writing `system.wav`, diarize the same `session_id` on Windows; expect sharing violation or nonsense segments. Alignment: transcript with one 6 s SYSTEM utterance covering two speakers (0–4 s / 4–6 s) — `align_all` → single id, `align_all_speakers` → `[0,1]`; confirm which the UI persists. Resource: run a live GigaAM meeting and diarize a ~1 h archive; watch RSS/GPU. Guards to add: refuse diarize unless session stopped and WAV is closed; `WaitForSingleObject`/timeout + `kill` the sidecar; lower `MAX_DIAR_SECS` or stream/chunk; don’t auto-sweep on files above a CPU budget; pause or reject diarize while live ORT is loaded.

**Net:** VAD/anti-hallucination and diar install atomicity are relatively tight. The production-risk core is **admission control inverted (spawn-then-permit)**, **retry loops that hold scarce permits with no breaker**, **in-process GigaAM as a single point of deadlock**, and **diarization as an unbounded blocking sidecar** that can fight live capture for the same WAV/GPU.
